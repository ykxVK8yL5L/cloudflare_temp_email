# 邮件工作流

邮件工作流用于定义收到邮件后的自动处理流程。管理员可以在管理后台的「工作流」页面通过可视化画布创建流程、测试流程并查看运行历史。

## 节点

- 触发器：收到邮件。每个流程必须且只能包含一个触发器。
- 条件：按发件人、收件地址、主题、正文、附件和提取结果分支，支持相等、包含、前后缀和正则匹配。
- Switch：针对一个字段配置 1–10 个有序 case。系统执行第一个匹配的 case；全部不匹配时执行 default 分支，适合在单个工作流中处理多类邮件。
- 处理：可配置内容提取、持久延迟。内容提取可从主题、发件人、收件人、纯文本正文、HTML、原始邮件或“主题 + 正文”读取；支持项目现有的智能验证码/链接提取，也支持自定义正则和捕获组。
- 动作：Webhook、转发、自动回复、拒收和停止流程。

提取结果会写入 `extract.type`、`extract.result` 和 `extract.result_text`，可供后续条件节点与 Webhook 模板使用。Webhook 模板使用双花括号变量，例如字段 `subject`、`text` 和 `extract.result`。系统会附加 `X-Workflow-Run-Id` 与 `X-Workflow-Node-Id`，接收方可用它们实现幂等处理。

## 部署

先执行 `db/2026-09-29-workflows.sql`，或在管理后台运行数据库迁移。然后在 Worker 的 `wrangler.toml` 中配置持久工作流：

```toml
[[workflows]]
name = "email-workflow"
binding = "EMAIL_WORKFLOW"
class_name = "EmailWorkflow"
```

未配置该绑定时，只能保存由条件、转发、自动回复、拒收和停止节点组成的同步流程。Delay、内容提取和 Webhook 节点需要此绑定。

转发、自动回复和拒收依赖正在处理的 SMTP 会话，因此必须位于所有持久节点之前。服务端会拒绝包含循环、不可达节点或不合法顺序的流程。

Switch 的每个 case 和 default 都必须连接下一节点。case 顺序即匹配优先级；多个 case 同时满足时只执行排在最前面的一个。

普通处理和动作节点只允许一个上游连接；停止节点可以被多个条件或 Switch 分支共同连接，便于多条路径汇合后结束流程。

## 执行与重试

启用的流程按优先级从高到低运行。外部动作默认失败后重试两次，可在节点上配置 0–5 次。Delay 最长为 30 天。每次执行及节点输出都会写入 D1，供管理后台查看。

运行历史支持单条删除和勾选后批量删除（每次最多 100 条）。删除运行记录时会同时删除它的全部节点记录；正在运行的记录不能删除。

Webhook 采用至少一次投递语义：极少数情况下，外部服务已接收请求但执行结果未能保存，重试会造成重复投递。Webhook 接收方应使用系统附加的运行 ID 和节点 ID 去重。

默认情况下，工作流作为现有收信处理链的补充。启用「跳过原有处理链」后，只执行工作流定义的动作；邮件仍会正常入库。

测试运行使用指定邮件 ID，留空时使用数据库中最新邮件。测试不会执行依赖原始 SMTP 会话的转发、自动回复或拒收节点。
